# Candle + KVCacheX: CPU reference integration benchmark

Generated by `scripts/candle_bench.sh` from `raw/*.json`; do not edit by hand.

**What this measures.** Candle 0.11.1 runs the llama2.c TinyStories model `stories15M.bin` (6 layers, dim 288, 6 heads, 6 K/V heads, context 256, f32) on the **CPU**, with two KV caches:

* `candle-native`: Candle's unmodified model and cache (a contiguous tensor per layer, grown with `Tensor::cat`);
* `kvcachex`: the same model, weights and Candle ops, with K/V in KVCacheX paged blocks (prefix cache off);
* `kvcachex-prefix`: the same, with KVCacheX's exact prefix cache on.

**Workload.** Closed loop in one process: all requests arrive at t=0, up to *C* are in flight, and each step runs **one model forward per in-flight request** (batch size 1, round-robin). This is not batched execution and not an inference server. Greedy decoding, fixed generation length. Arms are interleaved and their order rotates every repetition; numbers are medians over repetitions.

* *throughput*: generated tokens / wall time of this interleaved workload;
* *TTFT (queue-incl.)*: t=0 to a request's first token, **including** time waiting behind earlier prompts;
* *prefill*: duration of the request's own prefill forward pass;
* *ITL*: time between consecutive tokens of one request (includes other requests' steps when C > 1);
* *KV peak / alloc*: K/V bytes held for live requests at peak, and bytes allocated (KVCacheX preallocates its whole block pool; Candle allocates on demand);
* *Rust heap peak*: peak Rust heap growth during the run (global allocator), **not process RSS**.

Hardware: Apple M1; 8 (4 performance and 4 efficiency); 8 GB (macos/aarch64), rustc 1.99.1 (58cf8f9c3 2026-10-13), RAYON_NUM_THREADS=4.

## Summary

* **Noise floor:** on `unique` the two KVCacheX arms do identical work (0 prefix hits) yet their median throughput differs by up to 13%. Throughput differences smaller than that are not meaningful here.
* **shared-prefix, C=1:** prefix reuse cut prompt tokens computed 1388 → 428 and prefill p50 34.0 → 15.5 ms; peak KV in use 1.78 (native) vs 1.90 MiB. Throughput 193 (native) / 181 (kvcachex) / 205 (kvcachex-prefix) tok/s.
* **shared-prefix, C=4:** prefix reuse cut prompt tokens computed 1388 → 300 and prefill p50 42.4 → 17.3 ms; peak KV in use 7.05 (native) vs 5.06 MiB. Throughput 160 (native) / 150 (kvcachex) / 148 (kvcachex-prefix) tok/s.
* Without reuse, KVCacheX was between 0.85× and 1.03× native throughput: slower on 3 of 4 configurations (it adds a block-table gather on every step), by amounts comparable to the noise floor.
* Every arm produced exactly the native cache's greedy tokens in every timed repetition: yes.

## Caveats

* CPU only. Nothing here is a GPU, CUDA or T4 result, and nothing is a production-serving speedup.
* Gains with the prefix cache come from **not recomputing shared prompt prefixes** (fewer prefill tokens). Candle's native cache has no cross-request reuse, so the comparison is native-without-reuse vs KVCacheX-with-reuse on a workload built to have shared prefixes; the `unique` workload shows the case with nothing to reuse.
* Without reuse, KVCacheX's paged path does the same work as Candle's `Tensor::cat` cache plus a block-table gather; differences there are overhead/noise of this reference implementation, not a kernel-level claim.
* KVCacheX rounds K/V to whole blocks and preallocates its pool, so its KV bytes can exceed the native cache's at low concurrency; sharing reduces blocks in use when prompts overlap.
* A 15M-parameter model on one CPU process: absolute numbers are small and vary between runs (M1 P/E cores, thermal state); compare arms within one report only.
